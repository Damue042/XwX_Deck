## 更新助手审查

原实现将系统接受启动请求视为启动完成。
随后删除包含旧应用的暂存目录。
这不能证明新版窗口或后端已经正常运行。

首次修复只保留换出的旧应用，不再误报成功。
后续补上了两阶段启动健康通道。
新版访问数据前，先向指定签名助手申请许可。
后端和首个 React 界面就绪后，再确认启动。
助手验证成功后才记录 `startupVerified: true`。

初次通信回归暴露了 Darwin 非阻塞继承问题。
接收连接后改为阻塞读取，并限制消息大小和绝对时限。
后续回归又暴露了最终确认的关闭竞态。
对端关闭后，Darwin 可能拒绝设置读取超时。
现通过 `poll` 等待剩余时限，再读取排队消息。
实际 socket 和关闭后读取的回归均已通过。
失败日志和首次输出保留在本地证据中。

初次实现尝试在系统拒绝启动时有限恢复。
审查发现瞬时进程检查不能排除并发手动启动。
因此，最终代码移除了自动回退分支。
启动失败时保留两份应用，并记录人工恢复要求。
新版可能已更新数据格式，人工恢复前需核对兼容性。
成功或失败均不自动清理备份。
旧确认文件、错误挑战、错误版本和无关进程均不能确认任务。
通道不能防御完全控制同一用户会话的攻击者。

这些结果来自测试进程、合成目录和实际系统调用。
目录夹具不是可执行的签名应用。
它们不能替代真实签名包替换、重启和失败恢复验收。
机制与后续矩阵见 [Mac 更新验收准备](../mac-update-acceptance-plan.md)。
本次新增模块为 `macos_update_health.rs`。
对应的共享清单登记仍待另一维护工作区核对。
